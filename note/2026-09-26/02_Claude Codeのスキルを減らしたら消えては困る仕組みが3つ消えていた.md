# Claude Codeのスキルを24個→7個に減らしたら、消えては困る仕組みが3つ消えていた

〔画像1：ヘッダー〕

> .claude のファイルが243件消えています。私が消したものではありません

こんにちは、ハルトです^^

これは先日、Claude Codeが作業の途中で僕に言ってきた報告です。消したのは僕でした。スキルが増えすぎたので、減るのを承知で片付けたんです。

ただ、そのとき一緒に消えたものの中に、**消えては困る仕組みが3つ**混ざっていました。しかも3つとも、消えてもエラーひとつ出しませんでした。

この記事は、Claude Codeのスキル・フック・ルールを整理しようとしている人向けです。**片付けで何が消えたか、なぜ気づけなかったか、次からどう点検するか**を、実際に使ったコマンドとAIへの頼み方まで全部書きます。長いですが、保存版のつもりで書いたので、片付ける前に読み返してもらえたらうれしいです。

## Claude Codeを軽くしたかった

前の記事でも書きましたが、いま個人でスマホアプリを作っています。要件定義からテストまで、ほぼ全部Claude Codeと一緒にやっています。

そのプロジェクトには、「ハーネス」と呼んでいる設定一式を入れていました。スキル（Claudeが呼び出せる手順書）、エージェント（作業を任せる専門の係）、ルール（守ってほしい決まり）、フック（決まったタイミングで自動で動くスクリプト）をまとめたものです。自分用のパッケージとして配っていて、コマンド1つで入れ直せるようにしてあります。

使っているうちに、これがだいぶ膨らんでいました。

- スキル 24個
- エージェント 10個
- ルール 22個

使っていないものも多かったので、ある日、ハーネスの中身を絞ってから入れ直しました。**減るのは分かっていましたし、減らしたくてやりました。**

結果はこうなりました。

- スキル 24個 → **7個**
- エージェント 10個 → **2個**
- ルール 22個 → **12個**
- 消えたファイル **243個**

すっきりした、と思っていました。

## 243ファイル消えて、気づいたのはPRを作るときの警告だった

入れ直したのは、Claude Codeが別の作業をしている最中でした。アプリの画面をひとつ直してもらっていて、僕はその横でハーネスを更新した、という順番です。

AIは画面の修正を終えて、プルリクエスト（変更をまとめて取り込む申請）を作りました。そのとき、コマンドが「**まだコミットしていない変更があります**」という警告を出しました。

AIはそこで足を止めて、冒頭の報告をしてきました。

> .claude のファイルが243件消えています。私が消したものではありません

続けて「意図した削除かもしれないので、私の判断では戻しません。心当たりがなければこのコマンドで戻せます」とも書いてありました。勝手に巻き戻さなかったのは助かりました。

僕は「途中でハーネスのアップデートをやりました」と返しました。ここまでは、よくある片付けの話です。

問題は、ここからでした。

## 1つ目：mainへのpushを止めるフックが、エラーも出さずに外れていた

AIは消えたものを調べ始めて、すぐにこう報告してきました。

「フックのスクリプトが、フォルダごと消えています。**でも settings.json は24か所で、そのスクリプトを呼び出したままです**」

〔画像2：設定は24か所で呼び出したまま、呼び出す先が空〕

Claude Codeのフックは、`.claude/settings.json` に「このタイミングで、このスクリプトを動かす」と書いておく仕組みです。僕の設定には24本のスクリプトが登録されていました。

片付けで消えたのはスクリプトの本体だけで、**settings.json の登録は残っていました**。呼び出し先の無いフックが、毎回呼び出されている状態です。

なかでもいちばん大事だったのが、`git-guard` というフックでした。

これは、main ブランチへの直接のコミットや push、force push を**機械的に止める**見張り役です。AIがうっかり main に書き込もうとしても、このフックが「禁止です」と返して止めます。僕が安心してAIに git 操作を任せられていたのは、これがあったからです。

それが、黙って外れていました。

**エラーは出ていません。** 少なくとも僕の画面には何も出ませんでした。フックが動かなくても、Claude Codeの作業はふつうに進みます。止めてくれる役がいなくなっただけで、止められるはずの操作は全部通る状態でした。

さらに笑えないのが、消えたスクリプトの中に `check-hooks-alive` があったことです。**フックが生きているかどうかを、起動時に確かめるためのフック**です。見張りを見張る役まで、一緒に消えていました。

## AIは「従い続けます。でも歯止めは外れています」と言った

このときのAIの報告で、いちばん印象に残った一文があります。

> 規約としては生きているので私は従い続けますが、機械的な歯止めは外れています

僕のプロジェクトには、AGENTS.md（AIに向けた決まりごとを書いたファイル）に「main では作業しない。必ずブランチを切る」と書いてあります。こっちは片付けでは消えていません。

だからAIは、その日もちゃんとブランチを切って作業していました。**決まりは守られていた**んです。

〔画像3：規約は残る。歯止めだけが消える〕

でも、それは「AIが守ると決めているから守られている」状態です。フックがあったときは、AIが守り忘れても止まりました。フックが消えたあとは、守るかどうかがAIの判断ひとつに戻っていました。

書いてある決まりと、機械で止める仕組みは、似ているようで別物です。**片付けで消えるのは、たいてい機械のほう**です。決まりは文章なので残りますし、残っているので「まだ守られている」ように見えます。

僕は「フックは使い続けたいので戻して」と頼みました。

AIは消えたフック一式を戻したあと、2つ確かめてから報告してきました。

1. settings.json が呼び出している24本が、全部あるか → **24本すべてある。欠けは0本**
2. `git-guard` が本当に止めるか → **わざと main への force push を渡したら「禁止です」が返ってきた**

「**在るだけでなく、動いています**」という報告でした。この「在る」と「動く」を分けて確かめるやり方は、あとの手順でそのまま使います。

## 2つ目：要件定義の検査スクリプト

AIは続けて、もうひとつ報告してきました。「要件定義を機械で検査するスクリプトも消えています」。

僕のアプリでは、要件定義書を77ページぶん書いています。ページ同士のリンク切れや、要件の番号がかぶっていないかを、スクリプトで一気に検査していました。**その日の朝、同じセッションで実際に使っていたもの**です。

こっちは「使えなくなったもの」として、AIがちゃんと一覧に挙げてくれていました。僕は「req-check も戻して」と頼んで、AIが戻して、1回流して動くのを確かめました（77ページ・エラー0件）。

ここまでで、AIは「整理が終わりました」と報告して、プルリクエストをマージしました。僕もそれで終わったと思っていました。

## 3つ目：20分後、気づいたのは僕だった

マージから約20分後。僕はAIに「動作確認のサイトを開いて」と頼みました。

AIは、アーティファクト（Claudeがその場で作るWebページ）で動作確認のページを作ろうとしました。

ここで僕は手を止めさせました。

「ちょっと待って、なぜアーティファクト？ハーネスに組み込んでるでしょう？」

僕のハーネスには、要件定義書や設計書、テスト仕様書をレビュー用のWebサイトにする仕組みが入っていました。いつもはそれで作っていたので、アーティファクトが出てくるのはおかしい、と思ったんです。

AIが調べ直して、こう答えました。

「おっしゃる通りで、私が間違っていました。**サイトを作る仕組みも今日の更新で消えていて、私はそれを戻さないままマージしていました**」

〔画像4：24→7で消えた3つ〕

1つ目と2つ目はAIが見つけました。3つ目は、**AIが見落としたまま「終わりました」と報告して、マージまで済んでいた**ものです。僕が気づいたのも、たまたまその日に動作確認のサイトを開こうとしたからでした。開いていなければ、次に要件定義のレビューをする日まで気づかなかったと思います。

このサイトを作る仕組みは、あとでハーネスの宣言を1行足して入れ直したら、まとめて戻ってきました。

## 3つとも「呼ばなくても黙って働いていたもの」だった

あとから3つを並べてみて、共通点に気づきました。

| 消えたもの | 普段どう動いていたか |
|---|---|
| mainを守るフック | 自分からは呼ばない。危ない操作のときだけ勝手に止める |
| 要件定義の検査 | 検査のたびに裏で呼ばれる。結果だけ見ていた |
| サイトを作る仕組み | 「サイトを開いて」と頼むと、裏で呼ばれていた |

**3つとも、僕が名前を呼んで使う道具ではありませんでした。** 別の何かの裏で、黙って働いていたものです。

片付けるとき、僕は「このスキル、最近使ったっけ？」で残すものを決めていました。でも、この聞き方だと、**名前を呼ばずに使っているもの**は全部「使っていない」側に入ってしまいます。

使っていない道具を消しても、困ることはありません。困るのは、**使っていると気づいていなかった仕組み**が消えたときです。しかもそういう仕組みほど、消えても何も言ってきません。

だから片付けるときは、「使っているか」ではなく「**何かの裏で動いていないか**」で見る。そのうえで、片付けたあとに「在るか」と「動くか」を分けて確かめる。これが、今回の件で僕が変えたことです。

ここから下は、実際にやっている点検の手順を全部書きます。

## 片付ける前と後の点検、全手順

〔画像5：点検の4ステップ〕

手順は4つです。

1. 片付ける前に、黙って働いているものを書き出す
2. 片付けたあと、設定の呼び出し先と実物を照合する
3. 「在る」だけでなく「動く」を確かめる
4. 決まりごとのズレを直して、次の落とし穴をメモする

コマンドは、僕の環境（Mac・Claude Code）で実際に流して動いたものだけを載せています。

### 手順1 片付ける前に、黙って働いているものを書き出す

片付ける前に、Claude Codeにこう頼みます。**ここがいちばん大事です。** 消したあとに探すより、消す前に書き出すほうがずっと楽です。

```
これから .claude 配下のスキル・エージェント・ルールを整理します。消す前に、
「名前を呼ばなくても裏で動いているもの」を全部書き出してください。

調べてほしい場所：
- .claude/settings.json と settings.local.json の hooks（何のタイミングで、どのファイルを動かしているか）
- CLAUDE.md・AGENTS.md の中で、スキルやスクリプトを名前で呼んでいる箇所
- スキルの中から、別のスキルのスクリプトを呼んでいる箇所
- package.json の scripts や Makefile など、.claude 配下のファイルを参照している箇所

それぞれについて、
「何の役か」「消えたら何が起きるか」「消えたときにエラーが出るか」を表にしてください。
消えてもエラーが出ないものには印を付けてください。
```

最後の「**消えたときにエラーが出るか**」が効きます。今回の3つは全部「出ない」側でした。印が付いたものは、片付けで消えないように別の場所に移すか、消えたらすぐ分かるようにしておきます。

僕のプロジェクトで書き出すと、たとえばこうなります。

- フック24本（mainを守る・作業メモの書き出しと復元・ログ など）→ 消えてもエラーは出ない
- 要件定義の検査 → 呼ぶと「ファイルが無い」エラーは出るが、呼ばなければ気づかない
- サイトを作る仕組み → 同上。しかもAIは代わりの手段（アーティファクト）で埋めようとする

3つ目の「代わりの手段で埋めようとする」は、今回初めて知りました。AIは道具が無いと、黙って別のやり方で仕事を終わらせようとします。**結果が出てしまうので、道具が消えたことに気づきにくい**んです。

### 手順2 片付けたあと、設定の呼び出し先と実物を照合する

片付けたら、settings.json が呼び出しているファイルが全部あるかを、**機械で数えます**。目で追うと見落とすので、数で確かめます。

プロジェクトのフォルダで、これを流します。

```bash
python3 - <<'EOF'
import json, os, re
cmds = []
for f in [".claude/settings.json", ".claude/settings.local.json"]:
    if os.path.exists(f):
        for groups in json.load(open(f)).get("hooks", {}).values():
            for g in groups:
                cmds += [h.get("command", "") for h in g.get("hooks", [])]
root = os.getcwd()
paths = set()
for c in cmds:
    c = c.replace("${CLAUDE_PROJECT_DIR}", root).replace("$CLAUDE_PROJECT_DIR", root)
    paths |= set(re.findall(r'[^\s"\']+\.(?:js|cjs|mjs|sh|py)', c))
missing = sorted(p for p in paths if not os.path.exists(os.path.expanduser(p)))
print(f"参照 {len(paths)} 本 / 欠け {len(missing)} 本")
for p in missing:
    print("  欠:", p.replace(root + "/", ""))
EOF
```

settings.json に書かれたフックのコマンドから、スクリプトのファイル名（.js／.cjs／.mjs／.sh／.py）を抜き出して、実在するかを1本ずつ確かめるだけの小さなスクリプトです。

結果はこう出ます。

- 戻したあとの僕の環境 → `参照 24 本 / 欠け 0 本`
- 片付けた直後の状態を再現したもの → `参照 24 本 / 欠け 24 本`（消えたファイル名が24行並ぶ）

**欠けが0本でなければ、そのフックは黙って死んでいます。** ファイルの形式やパスの書き方は環境によって違うので、自分の settings.json に合わせて直してください。自分で直すのが面倒なら、Claude Codeにこう頼めば同じことをやってくれます。

```
.claude/settings.json と settings.local.json の hooks に登録されているコマンドから、
呼び出しているスクリプトのファイルを全部抜き出して、実在するか確かめてください。
結果は「参照 N 本 / 欠け M 本」の形で出して、欠けているものは全部名前を挙げてください。
目で数えずに、スクリプトを書いて機械で数えてください。
```

「**目で数えずに、機械で数えて**」を入れておくのがコツです。入れないと、AIがファイルを眺めて「全部あります」と答えることがあります。

### 手順3 「在る」だけでなく「動く」を確かめる

ファイルが在っても、動くとは限りません。中身が古い版に戻っていたり、読み込む先のファイルが別に消えていたりすることがあるからです。

なので、戻したものは**実際に1回動かして**確かめます。

**見張り役のフックは、わざとダメな操作を渡して、止めるかどうかを見ます。** 僕はこうしました。

```bash
echo '{"tool_name":"Bash","tool_input":{"command":"git push --force origin main"}}' \
  | node .claude/skills/harness-hooks/scripts/git-guard.js
```

これは本物の push をするわけではありません。「AIがこのコマンドを打とうとしている」というデータをフックに直接渡して、フックの返事だけを見ています。返ってきたのはこうです。

```
"permissionDecision":"deny"
"permissionDecisionReason":"保護ブランチ 'main' への force push は禁止です"
```

`deny`（拒否）が返ってくれば、見張り役は生きています。何も返ってこなかったり、エラーで落ちたりしたら死んでいます。

ほかの道具は、ふつうに1回流します。僕の要件定義の検査なら、流して「77ページ・エラー0件」が出るのを見ました。サイトを作る仕組みなら、実際にサイトを1回作ります。

Claude Codeに頼むなら、こうです。

```
戻したフックとスクリプトが「在る」だけでなく「動く」ことを確かめてください。
- 止める役のフック（保護・ガード系）は、止めるべき操作を入力として渡して、拒否が返るかを見てください。
  本物のコマンドは実行せず、フックに入力を渡すだけにしてください。
- それ以外のスクリプトは1回実行して、正常に終わるかを見てください。
「在る」と「動く」を分けて、表で報告してください。
```

「**本物のコマンドは実行せず、フックに入力を渡すだけ**」は必ず書いてください。書かないと、確かめるために本当に危ない操作を打とうとする可能性があります。

### 手順4 決まりごとのズレを直して、次の落とし穴をメモする

最後に、AGENTS.md や CLAUDE.md を見直します。片付けたあとも、**決まりごとのファイルは消えた道具を指したまま**になっていることが多いです。僕のときも、どちらも消えたスキルを名前で呼んだままでした。放っておくと、次のセッションのAIが存在しないスキルを呼ぼうとします。

ここでひとつ、AIが良い判断をしてくれました。消えたスキルの記述を**黙って削らず、「使えなくなった」と書いた**んです。

理由はこう説明されました。「記述ごと削ると、そんな手順は元から無かったように読めてしまう。なぜ設計書を作り直せないのかが、次に読む人に伝わらない」。

なるほど、と思いました。片付けの記録は、消した事実ごと残したほうがいい。いまはこの形にしています。

- 消えたスキル → 「もう無い。〇〇は手で直す前提」と書く
- 戻したもの → 「パッケージの管理から外れている。**次に更新するとまた消える**」と書く
- 今回の件 → 落とし穴として、手順2と手順3のコマンドと一緒に残す

AIへの頼み方はこうです。

```
AGENTS.md と CLAUDE.md を見て、いま存在しないスキル・スクリプト・エージェントを
指している箇所を全部挙げてください。
直すときは、記述を黙って削らずに「使えなくなった」「代わりにこうする」と書いてください。
あわせて、今回の片付けで消えて戻したものを「落とし穴」として残し、
次に片付けたあとに流す確認コマンドも一緒に書いてください。
書いたコマンドは、実際に流して動くことを確かめてから残してください。
```

最後の一文も大事です。**動かないコマンドを「確認手順」として残すと、次の自分がそれを信じて同じ穴に落ちます。**

## 使うときの注意

- 手順3の「わざとダメな操作を渡す」は、**フックに入力を渡すだけ**にしてください。本物の force push や削除を打って確かめるのはやめましょう
- 手順2のスクリプトは、settings.json に書かれたファイル名を拾うだけの簡単なものです。コマンドの書き方によっては拾えないことがあるので、「参照 N 本」の数が自分の登録数と合っているかも見てください
- `.claude/settings.json` は、Claude Codeが自分で書き換えられないようになっています。フックの登録を直すときは、AIに完成形を書き出してもらって、自分の手で反映します
- 手元に戻したフックやスクリプトは、パッケージの管理から外れます。次に入れ直すとまた消えるので、手順4のメモを必ず残してください
