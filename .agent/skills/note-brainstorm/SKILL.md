# noteネタ探しブレスト壁打ちスキル（2026-07-20作成）

ネタが決まっていない状態から、対話でネタ→構成→原稿を確定させ、`note-draft-post` スキル（一発投稿フロー）に引き渡すまでの手順。

## 大原則

1. **手ぶらで質問しない**。壁打ちを始める前に必ずPhase 0の材料集めを行い、具体的なネタ候補を自分で仕込んでから聞く。抽象的な選択肢（「実演系にしますか？」だけ）を投げない
2. **AskUserQuestionで細かく刻んで聞く**。ただし関連する質問は1回の呼び出しに最大4問までまとめて、往復回数は減らす。フェーズをまたいで先走らない（ネタ確定前に構成を聞かない）
3. **下記の質問項目は「例」であり固定リストではない**。記事の性質に応じて不要な質問は削り、必要な質問（例：連載の続き物なら前回との接続、商談体験記なら匿名化の度合い）を追加してよい。毎回同じ質問を機械的に繰り返さない
4. **承認ゲート（🚦）を勝手に飛ばさない**。ゲートは「ネタ確定」「構成確定」「原稿確定」の3つ。ゲート通過後は次のゲートまで質問攻めにしない
5. 文体・運用の既存ルールに常に従う：ハルトの口語（「^^」「！」あり・AIっぽい体言止め見出し禁止）／盛らない（指示文・AI回答は実物どおり）／実演は全部ダミーデータ／日付フォルダは作成日基準／`note/images/` を日付ミラーで同時作成／X告知はnote自動共有（フック投稿不要）

## Phase 0. 材料集め（質問する前に必ず・報告は1〜2行でよい）

以下を読み、**ネタ候補を最低5本**自分で仕込む：

- `.agent/handoff/HANDOFF.md`・`.spec/TODO.md` … 直近の実戦・出来事・引き継がれたネタ相談（前セッションで「note⑧のネタ候補」等が既に挙がっていることが多い。あればそれを最優先で候補に入れる）
- `note/` 配下の過去記事一覧 … 既出テーマの重複回避／シリーズのナンバリング確認（実演◯・ノウハウ◯の連番）／派生・続編候補の発見
- `x/` 配下の直近小ネタ … 反応が良かった・手応えのあったネタの深掘り候補
- `.agent/memory/MEMORY.md` … 発信戦略との整合
- `.output/phase0/26_note新シリーズ設計.md` … **2026-08-11に決めた新シリーズの設計**（読者＝中小企業のバックオフィス・ひとり社長／課題軸／連番なし／有料化の階段／最初の10本ラインナップ）。**ネタ候補はまずこの「最初の10本」から拾う**
- `.output/demo01_相談受付デモ/`・`demo02_期限管理デモ/`・`demo03_在留資格転記チェック/` … **すでに動く実装が3本ある**。中小企業向けに読み替えるだけで実演できる＝ネタの一次素材

### ネタの引き出し（候補を仕込むときの観点・参考記事より）

| ネタ源 | 具体的には |
|---|---|
| 直近の実戦 | 今週AIでやったこと・作ったもの・失敗したこと（失敗体験は特に強い） |
| X小ネタの深掘り | 140字で出したネタを記事1本に展開 |
| 読者の悩み逆算 | 「一人事業主 ◯◯ 面倒」で検索されそうな悩み（転記・メール・請求書・タスク管理…）。Yahoo知恵袋・X検索でリアルな悩み語彙を拾うのも可 |
| 過去記事の派生 | 続編・別角度・「あの記事のあれ、実はこうやってる」（シリーズ機能・内部リンクで繋ぐ） |
| よくある質問 | 人に聞かれたこと・説明したことはそのまま記事になる |
| メタネタ | 発信活動そのものを題材にする（「この記事はAIが下書きした」等） |

### ネタ選定基準（実績データより・2026-07-25の分析で確立）

**候補を5本仕込む段階で、この基準でふるいにかける。** 根拠＝noteダッシュボード全期間の実測（公開13本／ビュー599／スキ81／コメント0）。詳細は `.spec/KNOWLEDGE.md`「noteアクセス実績の分析(2026-07-25)」。

| 効くもの（優先して候補に入れる） | 効かないもの（候補にするなら切り口を変える） |
|---|---|
| **読者の不安・つまずきに答える**（AIが間違えたら／任せて大丈夫か／言っても効かない）＝スキ率17〜33% | **できたことの成果報告**（実演で〇〇できました）＝スキ率2〜4%。ビューは取れるがスキにならない |
| 失敗・引き算の話（「やめたら」「効かない」「気づけるように」） | 機能紹介・すごさ自慢（読者の行動が変わらない＝「すごいね」で終わる） |
| 考え方の転換を1つ持ち帰らせる | 実物・テンプレの丸ごと公開（保存されるがスキ0の実績あり） |

- **実演系を出すときは、必ず"不安の切り口"を被せる**。機能の紹介ではなく「その作業で不安なのはどこか／どう確かめるか」を主題にする（例：PDF→Excel転記なら「手入力の転記を信用できない問題をどう確かめるか」）
- **タイトルに読者の心の声を入れる**。効いている語彙＝**引き算・失敗・否定**（「やめたら」「効かない」「間違えても」）。弱い＝「できました」「公開します」＝書き手目線
- **この基準は母数が小さい実測（1記事12〜58ビュー）に基づく暫定版**。断定的に語らず、新しい実績が出たら更新する。数字をユーザーに示すときも「差は数件」であることを添える
- **コメントは全記事0**。記事末を「〜してみてください」ではなく**読者への問い**で閉じる型は未実験なので、候補に添えて提案してよい

### 記事の固定フォーマット（2026-08-11 全面改訂・課題軸シリーズへ移行）

**⚠️2026-08-11に「士業のAI実録」（vol.1〜21）を停止し、課題軸のシリーズへ切り替えた。** 設計の全文と根拠＝`.output/phase0/26_note新シリーズ設計.md`。旧フォーマット（`【士業のAI実録 vol.◯】`＋「正直な現在地」）はもう使わない。

**切り替えた理由**：直近6本が全部一桁スキ（2/5/1/6/2/1）。原因はタグの母数ではない（`#n8n` は2,879本＝`#士業` の1/4で1記事1,314スキ）。**伸びている4アカウントが絞っているのは「読者の属性」ではなく「読者が解きたい課題・使いたい道具」**で、「士業のAI実録」は属性＋実録＝課題語がひとつも入っていなかった。ハルトの最高記録（vol.13・27スキ）は唯一の道具軸の記事だった。

| 項目 | ルール |
|---|---|
| **読者（主語）** | **中小企業のバックオフィス（経理・総務・事務を1〜2人で回している人）・ひとり社長**。記事中の呼びかけもこの主語に揃える。※`.spec/KNOWLEDGE.md` の「高額リテイナーの本命は行政書士の顧問先中小企業（従業員5〜30人）」と一致＝事業計画とも矛盾しない |
| **軸** | **課題軸を本線**（請求書・問い合わせ・期限・議事録…を1本ずつ潰す）。**「新機能をいち早く仕事で試す」回を流入の当てとして間に混ぜる** |
| **タイトル** | **連番（`【vol.◯】`）を付けない。** 課題の言葉を前方に置く。型＝`〔課題〕を〔道具〕で終わらせる｜〇〇の全手順`。シリーズ性はアカウント名とプロフィールで担保する（n8n自動化ラボ方式） |
| **本文1行目** | **現場の生セリフから始める**。「こんにちは、ハルトです」は2行目以降に回す（旧シリーズから継続・有効） |
| **記事末（定型）** | 下記「締めの定型」を毎回そのまま入れる |
| **ハッシュタグ** | 固定5個＋可変3個まで（下記Phase 5参照） |

**なぜ連番を外したか**：伸びている3人（n8n自動化ラボ・さの氏・星ママ）のタイトルに連番は入っていない。連番を入れているのはK氏だけで、あちらは物語連載だから成立している型。課題軸で読者が検索するのは課題の言葉であり、連番は先頭12文字を食うだけで検索に効かない。

**締めの定型（課題軸版）**

```markdown
## 今日の1個

> （その記事から持ち帰れる一行。プロンプト・声かけ・チェック観点など、そのままコピペできる形で置く）

## 次に潰す課題

（次回どの課題を扱うかを1〜2行で予告する）

（記事ごとの問い1行）

スキ・フォローが続ける燃料になります🙌
```

- **「今日の1個」は必ず引用ブロックで囲み、コピペできる形にする**。ノウハウを地の文に埋めたままにしない（星ママ氏の「今日のコピペ」・n8n自動化ラボの両方が持っていて実証済み。持ち帰れる形にして初めてスキが付く）
- **「正直な現在地」は廃止**。物語連載（K氏）の型で、課題軸には合わない
- **問い1行は記事ごとに変える**。コメント獲得の実験を継続（旧シリーズ22本でコメント2件）
- **有料回のみ**、締めに「この記事の有料部分で得られるもの」を無料側に置いて中身を予告する（n8n自動化ラボの型）
- **締めの定型に更新頻度を書かない**（守れない約束にしない・2026-07-26判断を継続）。競合分析で成長要因として挙がっていた「**他アカウントへのスキ・コメント周り**」は頻度と別枠の施策として残る

**記事の連番管理は不要になった**（連番を付けないため）。過去記事の重複確認は `note/` 配下の一覧と `https://note.com/api/v2/creators/tonaria_ai/contents?kind=note&page=1` で行う。

**旧シリーズの扱い**：vol.21で自然停止。**告知記事は書かず、新シリーズを何も言わずに始める**（2026-08-11ユーザー判断）。公開済み22本のタイトル・タグは遡って直さない。

## Phase 1. 方向性のブレスト（AskUserQuestion）

仕込んだ候補を踏まえ、まず大枠を1回の呼び出しで聞く（例。記事状況に応じて増減）：

- **系統**：実演系（やってみた・スクショ主役）／ノウハウ系（考え方・コツ）／体験記系（商談・出来事）／メタ系。※シリーズのバランス（実演続きならノウハウを挟む等）を選択肢の説明に添える。**実績ではノウハウ系（特に不安に答える型）がスキ率で圧勝しているので、選択肢の説明に実測を一言添える**（例：「実演系はビューは取れるがスキ率2〜4%」）
- **ネタ元**：仕込んだ候補のうちどの源から出すか。**選択肢には必ず具体的な候補名を書く**（「直近実戦から：◯◯の話」のように）
- **読者に持って帰らせたいもの**：真似できる手順／考え方の転換／安心感（AI怖くない）／人間味・共感

回答が「その他」自由記入だった場合は、その内容で候補を仕込み直してからPhase 2へ。

## Phase 2. 🚦承認ゲート①：ネタ確定

Phase 0の仕込み × Phase 1の回答を掛け合わせ、**ネタ案3〜4本をAskUserQuestionの選択肢で提示**して1本選んでもらう。各選択肢に必ず添える：

- 仮タイトル（25文字目安・「誰が何をしてどうなったか」が見える形）
- 想定読者の悩み（1行）
- 見せ場（その記事の「おっ」ポイント）
- 必要素材（スクショの有無・撮影/生成の手間・追加のAPI実行や撮影が要るか）
- 懸念があれば正直に（例：商談前に手の内を公開することになる、素材が未撮影、など）

ユーザーが選んだ時点で**ネタ確定**。以降このネタでPhase 3へ。

## Phase 3. 構成の細部詰め（AskUserQuestion・ここが壁打ちの本体）

関連する質問をまとめつつ、以下の観点を刻んで聞く（例。記事により取捨選択・追加）：

**1回目の呼び出し（骨格）**
- **【必須・毎回聞く】ハルト本人の実態**：その記事が扱う行動を「実際にやっているか／やったことがあるか」を、構成を固める前に必ず確認する。**これを飛ばすと指南型になって書き手と主張がズレる**（vol.16「僕が消してる3つのクセ」＝その習慣が無かった／vol.17「学習させない設定」＝オンのまま・実名を入れたこともあった、と2本連続で判明して組み替えになった）。聞き方は選択肢型で「やっている／やっていない／確認したことがない／そもそも該当する場面が無い」。**「やっていない」が最強の素材になることが多い**——正直な立ち位置から入る実録型のほうが、指南型より強い記事になる
- **構成の型**：①体験談ベース型（いつ何を→動機→行動→結果→読者への一言）②問題解決・ノウハウ型（悩み提示→原因→解決策→事例→行動喚起）③ストーリー＋学び型（印象的な出来事→心情→転機→教訓→余韻）④実演記事テンプレート（`note/template/実演記事テンプレート.md`・実演系は原則これ）
- **導入の切り口**：あるある共感／印象的な一言・数字／前回記事からの続き／相談されたエピソード
- **記事の長さ感**：ライト（〜2,000字）／標準（2,500〜3,500字・シリーズの標準）／がっつり（4,000字〜）

**2回目の呼び出し（中身）**
- **盛り込むエピソード・見せ場**（multiSelect）：候補を具体的に列挙して選んでもらう。※盛らない原則＝実際にあったことだけを候補にする
- **画像プラン**：実物スクショ中心／Codex図解中心／両方。枚数と、撮影が必要なもの・既存素材で足りるものを明示
- **注意セクションの論点**：毎回書く「使うときの注意」に何を入れるか（ダミー鉄則・人間が最終判断・データの置き場所…から記事に合うもの）。※見出しは「使うときの注意」だけにする。「（大事なので毎回書きます）」等の注釈は付けない（2026-07-20ユーザー指示）

**3回目の呼び出し（タイトル）**
- **タイトル案4つ**を提示して選んでもらう。**連番（`【vol.◯】`）は付けない**（2026-08-11廃止・理由は上記「記事の固定フォーマット」）。型＝`〔課題〕を〔道具〕で終わらせる｜〇〇の全手順`。作るときのコツ：①**課題の言葉を前方に置く**（読者が実際に打つ検索語） ②内容が具体的に伝わる ③数字・疑問形で興味を引く ④感情・ストーリー性（「正直」「知らなかった」「〜してた」）。**全体で30〜48字**を目安。体言止めのAI臭いタイトルは候補に入れない
- **実績で効いている語彙を必ず1〜2案に入れる（2026-07-25）**：**引き算・失敗・否定**（「〜をやめたら」「〜は効かない」「間違えても気づけるように」）＝スキ率上位の共通点。逆に「〜できました」「〜公開します」だけの成果報告型は0〜4%だったので、それ単独の案を第一候補に置かない
- **SEO/AIO観点を常に意識する（2026-07-24ユーザー指示）**。タイトルと構成は「検索エンジン（SEO）」と「AI検索・生成エンジン（AIO＝ChatGPT/Perplexity等に引用・要約されること）」の両方で見つけてもらえる形に最適化する。具体的には：
  - **タイトル**：読者が実際に打つ検索語を前方に置く（例：ツール名「ChatGPT」＋機能名「定期タスク」＋「使い方/方法」＋悩み語彙「毎朝/自動化」）。口語の温度感は語尾で保つ（「〜してみた」等）。SEO重視かどうかは毎回ユーザーに確認してよい
  - **AIO対策（本文側・Phase 5で反映）**：①冒頭で「誰の何の悩みを、どう解決する記事か」を1〜2文で明言（AIが要約しやすい） ②見出しは質問・機能名を含む具体形にする（AIが該当箇所を拾いやすい） ③手順・比較は箇条書き/表で構造化 ④固有名詞（ツール名・機能名・数値）を正確に書く（AIの引用元として信頼される）。ただし文体はハルトの口語を崩さない——SEO/AIOは「構造と語彙」で効かせ、キーワードの不自然な連呼はしない

## Phase 4. 🚦承認ゲート②：構成確定

決まった内容を**アウトライン（見出し構成案）としてテキストで提示**する：

- 見出し（##レベル）と各節の要点1〜2行
- 画像の位置と内容（〔画像N：…〕形式）
- 文字数目安・ナンバリング（実演◯／ノウハウ◯）・ファイル名案

提示後にAskUserQuestionで「この構成で執筆OK／修正あり」を確認。修正ありなら該当Phaseに戻る。**OKで構成確定**。

## Phase 5. 原稿執筆 → 🚦承認ゲート③：原稿確定

- `note/YYYY-MM-DD/NN_タイトル（実演◯orノウハウ◯）.md` に原稿を書く（YYYY-MM-DD=作成日。`note/images/YYYY-MM-DD/` も同時に作成）
- **書き出す前に上記「記事の固定フォーマット」を必ず適用する**：①タイトル先頭に `【士業のAI実録 vol.◯】` ②本文1行目は顧客の生セリフ（挨拶は2行目以降） ③末尾に「今日の1個」＋「正直な現在地」の定型 ④主語は士業のひとり事務所
- 実演系はテンプレートの注意書きに従う：構造は使い回してOK・決めゼリフと繋ぎは毎回変える・「準備するもの」の連携手順は実演①へのリンク誘導
- 原稿末尾に「公開前チェックリスト」「撮影メモ」ブロックを付ける（noteには貼らない）
- 完成したら**要点サマリー（概要・見せ場・画像プラン・懸念）＋ハッシュタグ案を添えてユーザーにレビュー依頼**。修正指摘があれば反映して再提示。**OKで原稿確定**

### ハッシュタグ（2026-08-11改訂・課題軸シリーズ用）

**固定5個は毎回そのまま入れる。記事ごとに変えない。**

```
#生成AI  #AI活用  #DX  #業務効率化  #中小企業
```

- 設計＝**大タグで露出を稼ぎ、小タグで人気欄に載る**の二段構え。実測記事数（2026-08-11）＝#生成AI 461,281／#AI活用 263,316／#DX 99,403／#業務効率化 91,348／#中小企業 71,260。大2・中2・小1のバランス
- 旧固定タグからの変更＝**`#士業`（11,950）を `#中小企業`（71,260）へ、`#個人事業主`（91,370）を `#DX`（99,403）へ**。読者を中小企業のバックオフィス・ひとり社長に変えたため
- **可変枠は最大3個**。記事固有のツール名・機能名を足す。候補と実測＝#経営者 126,650／#プロンプト 109,219／#AIエージェント 52,204／#ClaudeCode 47,715／#社長 45,019／#NotebookLM 25,474／#GAS 11,801／#n8n 2,879／#請求書 2,789
- ※タグの母数は決定要因ではない（`#n8n` は2,879本しかないが n8n自動化ラボは1記事1,314スキ）。**中身が課題を名指ししているかのほうが効く**
- 固定運用にする理由＝タグを毎回変えると、そのタグページに記事が積み上がらない。さの氏（`niceduck`）は全166本で同じ5個を使い続けている
- 選定基準は「**読者が検索しそうな言葉**」（内輪の造語・誰も検索しないタグは入れない）
- 各タグに一言理由を添えて提示し、**noteへの設定はユーザーに残す**（公開ボタンと同じくユーザーの手作業）

## Phase 6. note-draft-postスキルへ接続

原稿確定後は `.agent/skills/note-draft-post/SKILL.md` の**一発実行フロー**へ引き渡す。**画像生成まではこのメインセッション（Opus）で、Chrome入稿以降はnote-posterサブエージェント（Sonnet固定）に委譲する**（工程ごとにモデルを分ける・2026-07-25）：

1. **メインで**画像生成（Codex委譲・ヘッダー1280×670はシリーズ統一テイスト・直前記事ヘッダーPNGを参照指定）／実物スクショの用意→`ls`＋`sips`＋Read目視で確認
2. **note-posterサブエージェントへ委譲**（Agentツール `subagent_type: "note-poster"`。「承認済み」明示＋原稿MDパス＋画像PNGパス＋ハッシュタグ案を渡す）：Chrome自動操作でnote下書き作成（本文HTML paste→画像挿入→保存→強制リロード検証）
3. サブエージェントがアイキャッチ設定→最終検証まで実行し報告
4. **ユーザーに残すのはハッシュタグ設定と公開ボタンのみ**、と完了報告に明記。その際**確定済みのハッシュタグ案をコピペできる形で再掲**する
5. 公開報告を受けたら：TODO.md更新→**ハンドオフ作成（`/handoff` の手順：既存 `.agent/handoff/HANDOFF.md` を `archive/YYYY-MM-DD-HHMM.md` にリネーム→新規作成）**→完了報告→コミット（コミットは完了報告後にまとめて・途中経過でコミットしない）
   - **ハンドオフはユーザーに聞かずに自動で作る（2026-07-26ユーザー指示）**。「公開した」の報告＝その記事の作業単位が完了した合図なので、毎回ここでハンドオフまでやる。TODO更新・ハンドオフ・コミットは同じ1コミットにまとめてよい

※このフェーズは note-draft-post 側の既定どおり「途中で質問せず一気に実行」。ただし原稿確定前に見切り発車しない。
